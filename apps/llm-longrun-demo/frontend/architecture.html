One problem, two fixes: Sync (blocking) vs SSE (streaming) vs Async (request + poll)

A long-running gpt-4o call takes longer than a request timeout allows. The sync (blocking) baseline shows the problem; the two standard fixes — SSE streaming (keep the connection alive by flowing tokens) and async request + poll (return a job id immediately, poll for the result) — both avoid it. All three travel the exact same infrastructure path and share one backend, one BFF and one frontend. The one tuned knob is the ALB idle timeout (~5s): low enough that the sync baseline visibly trips it, while a byte-every-few-hundred-ms SSE stream and a sub-second async submit both sail under it.

The timeouts are stacked on purpose. The ALB idle timeout (var.alb_idle_timeout = 5) sits below the API Gateway BUFFERED cap (29s) and CloudFront origin read (60s), and the bff read-timeout is raised to 60s — that bff→backend wait does not traverse the ALB, so if it were low the bff would 504 first and the ALB would never fire. A long sync request is held open with no bytes and is cut here. SSE flows a token every few hundred ms — each byte resets the idle timer, so it survives (and API Gateway routes the exact /api/chat to a STREAM integration to lift the 29s cap). Async returns a job id in well under a second, so nothing is ever held open long enough to time out.

The problem — Sync (blocking)

One request, held open

POST /api/chat/sync application/json

Browser
A single fetch('/api/chat/sync') then await response.json(). The connection stays open the whole time the model generates — the UI shows only a spinner and an elapsed timer. No bytes arrive until generation finishes.
Backend & BFF
Backend chatSync() returns Mono<FullResponse> — it blocks until the whole gpt-4o answer is collected (the same getFullResponse() the async job uses). The bff relays via RestTemplate; its read-timeout is 60s so it waits rather than failing early.
ALB — cuts the connection
No response bytes have flowed, so the inbound connection is idle. At idle_timeout = 5s the ALB closes it. A long answer routinely needs more than 5s, so the client gets a 504 (or a reset connection) before the answer is ready.
The takeaway
The higher caps (API Gateway 29s, CloudFront 60s) never get the chance to fire — the ALB is the binding limit. This is the exact failure the two fixes below avoid.

Fix 1 — SSE streaming

Tokens arrive progressively

POST /api/chat text/event-stream

Backend (WebFlux)
Streams the model output as a reactive Flux<ServerSentEvent>; Flux.concat(tokens, doneEvent) puts the [DONE] sentinel last. Each token is emitted the instant the model produces it. produces = TEXT_EVENT_STREAM_VALUE is required or Spring buffers the whole response.
BFF → ALB
The blocking bff uses StreamingResponseBody to read the upstream InputStream 512 bytes at a time and flush() each chunk — no buffering. Every flushed byte resets the ALB idle timer, so even with the 5s idle timeout the connection stays alive.
API Gateway
The explicit /api/chat resource uses response_transfer_mode = STREAM, so each SSE frame passes straight through instead of being buffered into one 29s-capped response (timeout raised to 15 min). Everything else goes through the greedy BUFFERED proxy.
CloudFront & Browser
CachingDisabled, so frames flow through the edge as they arrive. The browser reads with fetch() + response.body.getReader() (not EventSource, which is GET-only), parses event:/data: frames, and appends each token live — showing TTFB and a rising token count.

Fix 2 — Async (request + poll)

Submit, then poll

POST /api/chat/async GET /api/jobs/{id}

Submit → 202 immediately
Backend startAsync() writes a PENDING job to the selected store, kicks the LLM call off on Schedulers.boundedElastic(), and returns 202 with a job id in milliseconds. The request never waits on generation, so it is far under 5s.
Background job → store
Off the request thread the job goes PROCESSING, calls OpenAI, then writes COMPLETED (with the answer) or FAILED into the store — Redis/Valkey or DynamoDB, chosen per request. No client connection is held while this runs.
Poll → each request sub-second
The browser polls GET /api/jobs/{id}?store=… on an interval. Each poll is a tiny, fast request that reads one record and returns at once — nowhere near any infra timeout, no matter how long generation takes.
Result delivered
When a poll sees COMPLETED, the browser renders the full answer. Because no single request is ever held open, the low ALB idle timeout simply never applies.

Application internals

Three tiers sit on the path (frontend → BFF → backend), plus two interchangeable job stores for the async pattern. The backend is reactive (WebFlux / Netty); the bff is a thin blocking relay (Spring MVC / Tomcat). One OpenAiService feeds all three paths: streamResponse() → Flux<String> for SSE, and getFullResponse() → Mono<String> for both the sync baseline and the background async job — the only difference is whether a client request waits for it, a stream carries it, or a background job does.

Infrastructure

A standalone stack (no shared platform): one ECS Fargate task runs both JVMs (backend + bff), fronted by an ALB, API Gateway and CloudFront; the two job stores sit alongside. The ALB idle timeout is the one knob tuned specifically to make this demo's point, and API Gateway splits /api/chat (STREAM) from everything else (BUFFERED proxy).
