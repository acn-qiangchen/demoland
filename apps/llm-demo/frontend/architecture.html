2 つの呼び出しパターン：SSE ストリーミング vs ブロッキング REST

デモのトグルは、同じ gpt-4o の回答を取得する 2 つの方式を切り替えます。 どちらのリクエストも まったく同じ インフラ経路を通ります。違いは レスポンスの返り方 だけです。開いたストリーム越しにトークンを 1 つずつ返すか、 モデルの生成完了後に一度にまとめて返すか、です。

SSE ストリーミング

トークンが逐次届く

POST /api/chat text/event-stream

バックエンド（WebFlux）
モデルの出力をリアクティブな Flux としてストリーミング：Flux.concat(tokens, doneEvent) により [DONE] センチネルが最後に届きます。モデルが生成した瞬間に各トークンを送出します。 produces = TEXT_EVENT_STREAM_VALUE を指定しないと Spring が全体をバッファリングしてしまいます。
BFF → ALB
Spring MVC（ブロッキング）の StreamingResponseBody で上流 InputStream を 512 バイトずつ読み、都度 flush() してバッファせず中継します。ALB の idle_timeout = 300s により、トークン間隔が空いても長時間コネクションを維持します。
API Gateway
これを成立させているのが response_transfer_mode = STREAM です。各 SSE フレームが、29 秒制限のある 1 つのレスポンスにバッファリングされることなく、そのまま通過します。
CloudFront
CachingDisabled。フレームは到着するそばからエッジを通ってビューアーへ流れます。
ブラウザ
fetch() + response.body.getReader() で読み取ります（EventSource は GET 専用なので使いません）。event:/data: フレームを解析し、各トークンをリアルタイムに追記します。TTFB と増えていくトークン数を表示します。
ユーザーに見える様子ストリーミング中…
はい、回答をトークンごとにお返しします…

REST（ブロッキング）

回答をまとめて一度に

POST /api/chat/rest application/json

バックエンド（WebFlux）
生成が完全に終わるまでブロックし、その後 1 つの JSON ボディ { "content": "…" } を返します。生成が完了するまで何も送信されません。
BFF → ALB
RestTemplate（Apache HttpClient 5）の postForObject で 1 つの JSON ペイロードをそのまま通します。gpt-4o の完全な回答は 生成に 29 秒を超えることがよくあります。
API Gateway
こちらは BUFFERED（デフォルト）。レスポンス全体をバッファしてから返す従来型の REST 動作で、キャッシュ・ボディ変換・きれいなエラーステータスが使えます。代わりにタイムアウトは 29 秒が上限で、生成がこれを超えると 504 になります。
CloudFront
CachingDisabled。用意でき次第、1 つの JSON レスポンスを転送します。
ブラウザ
await response.json()。待機中はずっと スピナーと経過タイマーを表示し、その後、完全な回答を一度に表示します。TTFB はなく、トークン数は推定値です。
ユーザーに見える様子待機中…
回答全体を待機中…
はい、回答です。生成が完了したあと、ひとまとまりのブロックとして届きます。

アプリケーションの内部構成

経路上のアプリは 3 層（フロントエンド → BFF → バックエンド）です。注目すべきは バックエンドと BFF で Spring の Web スタックが異なる点で、バックエンドは リアクティブ（WebFlux / Netty・ノンブロッキング）、BFF はサーブレット （Spring MVC / Tomcat・ブロッキング）です。SSE の「トークンが逐次届く」性質は リアクティブなバックエンドで生まれ、ブロッキングな BFF は StreamingResponseBody のチャンク flush でそれを素通しします。
